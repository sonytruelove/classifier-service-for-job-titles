# classifier-service-for-job-titles
Выполнение тестового задания

Сервис сопоставления должностей из внешней системы со справочником-классификатором. Результат по всем 300 записям — `results.csv` в корне репозитория, данные — в `data/`, код — в `solution/`.

## Запуск

```
cd solution
pip install -r requirements.txt
python run.py
```

Результат — `results.csv` в корне репозитория (рядом с папкой `data`), по всем 300 записям `data/raw_positions.csv`.

Проверить качество на эталонной выборке:

```
python evaluate.py
```

Тесты:

```
pytest --cov=. --cov-report=term-missing
```

## Подход и обоснование

Подход.

Нормализация текста (регистр, пробелы, "N разряда"/"N категории", пометки вроде "(вахта)"/"(совм.)", названия организаций в кавычках, частые сокращения типа "маш." или "ЭГС") плюс fuzzy-сравнение нормализованной строки с каждым наименованием классификатора через rapidfuzz.
Отдельно завёл словарь профессионального жаргона — там, где слово по смыслу то же самое, но по буквам совсем другое: "шофер" — это "водитель", "оператор автокрана" — это "машинист крана автомобильного", "бульдозерист" — это "машинист бульдозера". Без этого словаря просто фаззи-мэтчинг эти пары не находит, там нет общих букв почти. Ещё добавил лёгкую коррекцию опечаток именно для таких ключевых слов ролей (оператор/крановщик/машинист и т.п.), потому что иначе опечатка в самом синониме рушит всю цепочку — обнаружил это на реальном прогоне, когда "операттор экскаватора" не находился, а "оператор экскаватора" находился.

Почему не что-то другое.

Смотрел три альтернативы и все три отверг, но по разным причинам.

Чистый точный/словарный матчинг отпал сразу — опечаток в данных слишком много, треть строк не совпадёт побуквенно с каноном.

Yargy (использовал её раньше в одном проекте с NER) — попробовал её morph_pipeline на этих данных: находит совпадение только для 99 из 300 записей. Она хорошо нормализует словоформы (падежи, число), но не толерантна к опечаткам — а тут именно опечатки основная проблема, не склонения. Чтобы её использовать, пришлось бы городить поверх ещё один слой фаззи-исправлений, и на этом этапе rapidfuzz уже проще и делает то же самое напрямую.

Локальная LLM. 
Скачал Qwen2.5-0.5B-Instruct (меньше вменяемой модели с русским почти нет), прогнал промптом со списком всех 56 должностей на 50 эталонных записях. На процессоре без AVX2 и без вменяемой видеокарты модель не осилила обработать хотя бы одну запись за разумное время, не стал ждать. Даже если бы дождался, для этой задачи генеративная модель — это лишняя случайность и непрозрачность там, где по сути нужен детерминированный алгоритм с понятной метрикой уверенности.

Пороги. 
Порог для принятия совпадения — 0.78 по score. Ниже — "нет соответствия". Отдельно: записи с 0.78–0.90 помечаю "требует проверки" — обычно там всё верно, но не настолько уверенно, чтобы пускать в данные без глаз человека. Для "нет соответствия" тоже есть свой порог для пометки на проверку (0.60) — если лучший кандидат не совсем далеко, лучше показать человеку, чем молча отбросить. Пороги подбирал прогоняя на labeled_sample.csv — там 50/50 (100%), но это маленькая выборка. Один слабый момент, который знаю и не стал фиксить искусственно: короткие названия должностей типа "юрисконсульт" или "фельдшер" по чистой похожести букв попадают в тот же диапазон score, что и реальные пограничные случаи вроде "специалист по сметам" (похоже на "сметчика", но не точно) — отличить одно от другого по score без дополнительных знаний нельзя, это ограничение подхода.

Если бы записей было 3 млн, а классификатор — 10 тысяч значений.

Текущая схема — это N*M сравнений в питоновском цикле, при таких объёмах это не взлетит вообще (30 млрд пар). Первое что сделал бы — дедупликация: в реальных данных одинаковые "как есть" названия повторяются массово, обычно уникальных строк на порядки меньше, чем всего записей. Дальше — не искать полным перебором, а строить индекс: триграммы в Postgres или Elasticsearch с fuzzy-запросом, либо vectorized batch через rapidfuzz вместо цикла по строкам. И кешировать решения по уже виденным строкам, чтобы не пересчитывать одно и то же.

Как бы улучшал дальше.

Самое дешёвое — завести очередь ручной проверки как источник данных: каждое подтверждение или исправление реального человека пополняет словарь синонимов, а не теряется. Второе — словарь жаргона у меня сейчас собран вручную по тому, что нашёл глазами в этих 300 строках, для продакшена его стоит сверить с официальными перечнями (ЕТКС/ОКПДТР), там наверняка есть готовые синонимические ряды. Третье — если пограничная зона (типа "специалист по сметам") окажется частой на реальных данных, а не разовым случаем, тогда уже имеет смысл добавить второй слой — эмбеддинги именно для таких семантических, не буквенных совпадений, но именно как дополнение поверх текущей логики.

Решение делал с помощью ИИ (Claude Code) ввиду ограничения по срокам (один день). Но подход, пороги и разбор данных — мои, ИИ был инструментом реализации и проверки гипотез.
